# Handoff: MIDI Tempo Fix

Read this before changing anything. It's the current state, not a history.

## What it is

A tool that checks and fixes Standard MIDI Files so every DAW plays them the same: the tempo map (`core.py`) and the notes (`notes.py`), both standard library only. It also compares a file with another MIDI file, a REAPER project or a recording (`audio.py`), and turns a file's markers, or markers typed in by bar and beat, into Ableton Live locators named for AbleSet (`ableton.py`, window `ableton_gui.py`). Two front ends: the `midi-tempo` command (`cli.py`: `check`, `fix`, `ableton`) and a wxPython app (`gui.py`). Updates come through Sparkle on the Mac and WinSparkle for installed Windows copies (`sparkle.py`, `winsparkle.py`), and `update.py` for the rest. Mac and Windows; the command also runs on Linux.

**Where it stands (2026-11-03):** 1.9.1 is released, signed and notarized, with signed update lists for both systems. It adds sets straight from REAPER projects, AbleSet lyrics tracks and exact curved tempo to Make Ableton Set. Both Macs run 1.9.1: the Studio through five real Sparkle updates in a row (1.8.0 to 1.8.1, 1.8.2, 1.8.3, 1.9.0, 1.9.1), the MacBook from the notarized zip over ssh. The MacBook's command is a clone at `~/midi-tempo-fix` pulled by `com.matthew.midi-tempo-fix-pull`, hourly since 2026-11-03 (it was 4 AM daily, and the log showed it failing every night with the laptop asleep or offline, stuck on 1.7.3 for three weeks). Not yet tried by a person: the Windows installer and WinSparkle on a real PC with a screen reader, and a set made on Windows opened in Live for Windows.

## The three file faults it fixes, and how each was proven

All found on 2026-10-11 from real REAPER 7.82 exports, measured rather than assumed:

1. **Doubled tempo event at a ramp's end.** REAPER wrote `84.7442` then `85.0` on the same tick at the end of a slowdown. The second is correct by the MIDI rules; an app keeping the first drifts (0.9 s by the end of that song). Logic played it wrong; the cleaned copy played right.
2. **REAPER ramp hints.** REAPER's export writes text meta events (type 1) reading `REAPER gradual tempo change start <bpm>` and `REAPER gradual tempo change interpolation end`. REAPER's import uses them to rebuild a smooth ramp, and when the ramp ends on a time signature change it places the end marker as if the tempo had stayed at the start value (127 to 90 over 6 beats came back as 6 beats of 127: 2.835 s instead of 3.318). Drift reached 543 ms. With the hints stripped, REAPER imported the same file as 166 square tempo markers, within 0.1 ms of the source project. Ramps ending on a plain tempo marker import fine even with hints, but stripping is harmless there too.
3. **Tempo map events on a later track** of a format 1 file. Tempo changes are always moved to track 0. Time signatures only move when track 0 lacks one at that tick: notation apps copy them to every track and that is harmless. Key signatures are per-track by design and never move. (Version 1.0 counted all three and called 3,000 of 17,000 files broken; the scan below caught it.)

Doubled tempo events only count when the values differ by more than 0.001 BPM. The same tempo written twice can't make apps disagree and is left alone. (1.0 flagged those too; 36 of the first 40 hits in the scan were this harmless kind.)

## The fourth fault: a bar REAPER's export makes whole (needs the project)

Found 2026-10-12 on Listening Forward. When a time signature marker lands partway through a bar, REAPER plays that bar short (here 79.15 beats into a 4/4 section, so the last bar was 3.15 beats). Its MIDI export makes the bar whole, so every event after the marker is pushed late by the missing 0.85 beat: 254 ms at 200 BPM. The tempo and time signature events move with it. Proven three ways: the project's own piano item notes (read from the `.RPP`, QN through the tempo envelope) against the export, 0.00 ms before the marker and +253.75 ms after, every note; the project's render against the export, a 253 ms step in the piano's rest across 4:14; and the corrected file against the render, within 10 to 15 ms everywhere.

The file alone can't show it, so it is only found and fixed with the project: `project_short_bars()` walks the project's time signature points (`PT` field 5: numerator in the low 16 bits, denominator above), `export_has_short_bar_fault()` requires a tempo or time signature event where the padded section starts and none where the project starts it, and `match_project_bars()` moves every event back by the padding before it. The time signature then lands partway through the bar again, as in the project. `compare_project()` checks for it first (at one steady tempo the beats still match, so the tempo comparison alone misses it). `fix_file(project=...)` verifies by reading back: the tempo map matches the project at every quarter beat within 1 ms, and every note kept key, velocity and order and moved by exactly the padding before it. The app enables Fix for such files after a comparison with the project (`project_for`); the command takes `fix --project X.RPP`, and `check --compare X.RPP` prints the exact fix command.

## Checking against a recording (`audio.py`)

`compare_with()` sends audio extensions to `audio.compare_audio()`. numpy is required (lazy import; the command says how to get it, the app bundles it and its `--self-test` fails without it). WAV is read directly (8/16/24/32-bit PCM, float, extensible, RF64); anything else goes through `afconvert` (every Mac) or `ffmpeg`.

Two passes:

1. **Coarse:** chromagram of the audio (4096-point frames at 22,050 Hz, 50 to 2000 Hz folded to pitch classes, C = 0 like MIDI keys) against the MIDI notes' pitch classes (decaying, drums left out), aligned by subsequence DTW with steps (1,1), (1,2), (2,1), so the recording may start and end anywhere and run at half to twice the speed. Off-diagonal steps cost `STEP_PENALTY` 0.5: without it the path swung by whole beats. Quality (mean cost where the MIDI plays) over 0.75 means "not the same music". The lag is smoothed two ways: 4 s running median (search centre and local slope) and 20 s (trend).
2. **Fine:** spectral flux every 88 samples (about 4 ms), against the MIDI's note starts in 12 s windows every 4 s. Each window scores every lag within `FINE_WIDE` 0.6 s of both the centre and the trend, following the local slope inside the window (a 3% tempo difference moves 360 ms over 12 s). The top 8 peaks plus "the trend" are candidates, and the windows choose together by Viterbi: a candidate costs its weakness (-log of peak over median) plus the cheaper of moving with the trend or staying put, scaled by `JUMP_COST` 0.01 s (+10% of the expected move).

`describe_offsets()` smooths with a running median of 3, splits the curve into straight runs (top-down, tolerance 30 ms or 1.5% of the total spread), drops one-point runs between others (a window straddling a jump measures something in between) and short excursions that return to where they left (a passage matched a beat or half a beat off), merges runs with the same slope and no step, then says each run: lines up, a steady offset, or a different tempo in BPM. Between runs it says a jump only if the two lines don't meet near the boundary (if they meet, it's a tempo change). `_find_jump()` places a jump at a note: each note votes for the old or new lag, and among equally good splits the one across the longest rest wins; a rest over 2 s is reported as a range.

Lessons, each a real bug found on real files:
- **Hops must be whole numbers of samples.** 4 ms at 22,050 Hz rounds to 88 samples, 3.991 ms: every time read 0.23% late, which looked exactly like a tempo difference. `FINE_HOP` is defined in samples; the chroma hop is rounded the same way.
- **Flux peaks 16 ms early** (a 46 ms window sees the attack before its centre reaches it), measured on synthetic plucks with 2.5 to 10 ms attacks. `audio_onsets()` shifts by that.
- **Rhythm repeats every 8th and 16th.** In 8 s windows, Fresh Air's repeated figures fit a 16th off almost as well as on; Sound Between Us an 8th. Longer windows, a stronger cost on moving, and the excursion rule fixed it.
- **The coarse path can be wrong at the end** where sparse chords sit half a beat apart (Fresh Air's last 15 s), and the trend inherits it. Searching around the trend as well as the centre, wide enough to reach the true lag, and making "stay put" always cheap fixed it.
- Truth for tuning comes from 20 s windows scored at fixed lags, which repeating rhythm can't fool; every real pair was measured that way first. The bench: eight real MIDI and recording pairs from Matthew's album (kept on his Macs, never in this repo), all must read right, plus the synthetic tests in `tests/test_project_and_audio.py`.

## Reports are verdict first

Every file's report starts with one line a listener can stop after: "name: clean." or "name: needs fixing. 2 problems: two tempos on one tick, REAPER ramp notes." (`verdict()`), then the details. More than one file adds `summary()` on top ("Checked 40 files: 3 need fixing, 37 clean."). In the app, more than `BRIEF_OVER` (20) files lists only the verdicts of files needing fixing; the command's `--brief` does the same per file. Inside a chosen folder, names include the subfolder, since names repeat across folders.

Status comes first because long names are cut off at the end of a row, and a listener should hear the answer before the name. Selecting a row puts that file's full `describe()` in the report without moving focus. VoiceOver reads "Files table, row 1 of 61, Needs fixing: ...".

## Using every core (`batch.py`)

`check_many` / `fix_many` run the per-file work in a `ProcessPoolExecutor` (spawn context on every platform: consistent, and safe next to the GUI's threads), all cores but one, `chunksize` scaled to the batch, results in the original order, progress as files finish, and a stop callback that cancels the rest. Below `PARALLEL_FROM` (8) files it stays on one core, since starting workers costs more. The 5,343-file library: 36 s to 3.4 s on the command line (20-core Studio), 4.2 s in the app; parallel and serial output are identical, and fixing all of Mutopia in parallel produces byte-identical files to fixing it serially.

Hard-won rules, all found by deliberately breaking it:
- **Every entry point needs `if __name__ == "__main__"`**, because spawn re-imports the main script in each worker. The `midi-tempo` launcher and `__main__.py` lacked it, and every worker re-ran the whole command.
- **The frozen app needs `multiprocessing.freeze_support()` first in `app.py`.** Without it, each worker is a whole new copy of the app, windows and all, and the batch hangs. Two nets catch a build that loses it: `gui.main()` exits at once when started with `--multiprocessing-fork` (so the pool breaks and the batch falls back to one core instead of piling up windows), and `--self-test` runs a real two-worker batch, waits at most 30 s, and checks `batch.last_run["parallel"]`, so a quiet fallback still fails the test.
- **Read a self-test through a file, never a pipe.** A broken build leaves Python's resource tracker alive, holding the pipe open, so `capture_output=True` waited forever. `build_app.py`, `release_mac.py` and the updater all use a temp file and a timeout.
- If the pool can't start or dies (`BrokenProcessPool`, `OSError`), the batch finishes on one core; the GUI catches anything else and ends the batch with a message rather than staying busy.

The app shows a Stop button and a progress bar (`wx.Gauge`) only while working; Escape also stops. A new batch clears the Files list and the status bar first, so no stale rows or messages sit beside a new run.

## Batches in the app

Checking and fixing run on a worker thread; every control is disabled meanwhile (`_set_busy`). Progress goes to the window title once a second, and roughly every 500 files `announce()` asks VoiceOver to say "Checked 1000 of 5343" (macOS AXAnnouncementRequested through the Objective-C runtime, like the report label; no extra dependency). Short confirmations (Report copied, Report saved) go to the status bar and `announce()`, so focus never moves. Files that can't be written next to their original are collected and handled after the worker, on the main thread, where the folder dialog can be shown. `reveal()` opens only the first copy when copies span more than three folders, so a big batch doesn't open dozens of Finder windows.

`Event` uses `__slots__` and computes `meta_type` once; as a property it was a third of the time on a big piano file. The 5,343-file library went from 48 to 36 seconds.

## SMPTE-timed files

A file whose header counts time in video frames (division's top bit set) has no tempo map; tempo events in it do not apply. It is modelled as a fixed 60 BPM with frames × ticks-per-frame ticks per beat, so one beat is one second and every time calculation stays the same code. Tempo checks are skipped, notes are checked and fixed, and the original header is written back unchanged. 29 means 29.97 (drop frame).

## Note problems (`notes.py`)

Duplicates, same-key overlaps, stuck notes and stray releases are fixed; zero-length notes are reported only. Overlaps on the drum channel (channel 10, index 9) are not counted or trimmed: drum hits are one-shots and drum performances overlap constantly. Before this rule, 881 of the 5,343 library files "needed fixing", mostly Groove drum performances; after it, 314.

Tempo map events moved to the first track are de-duplicated, keeping the LAST identical copy on each tick. Keeping the first was a real bug, found by training: in two LilyPond files the tracks disagree on one tick (120, then 60, then 120 again on other tracks), the last one read wins (120), and dropping the later copies handed the win to 60. Verification caught both, so no bad file was written; `test_merging_copies_keeps_the_tempo_that_wins` and the fuzz test's disagreeing copies now cover it (both fail on the old code). LilyPond (all of Mutopia) writes the tempo on every instrument track, and moving them all used to stack identical copies; the report says "moved 2 ..., merging 4 identical copies". Rebuilding pairs note-offs first in, first out, merges same-start duplicates (first velocity, longest end), ends an overlapped note at the re-strike, and ends stuck notes at the track's last tick. At one tick it writes note-offs, then other events in their original order, then note-ons; a zero-length note keeps on-then-off. Only tracks with a fixable problem are rebuilt.

Verification for note fixes: every note start (track, moment, channel, key, first velocity) is identical before and after, every non-note event is at the same moment, and the copy has nothing left to fix.

## Second review, 2026-11-03

A review of this half ran 17,120 real MIDI files through read, analyze, describe, fix and compare (0 crashes, 0 failed verifications) and 3,000 fuzzed ones, then found seven faults that only corrupt or unusual input reaches. Each was reproduced, fixed and is kept by a test:
- One bad file used to end a whole batch with a traceback (command exit 1, the "needs fixing" code). `read_midi` now refuses a channel event cut short, a tempo event that isn't 3 bytes or is 0, and a header with 0 ticks per beat; `batch._check_one` / `_fix_one` also catch anything else per file.
- A time signature with numerator 0 or a denominator past 64 is skipped (`time_signatures`), and `bar_beat` never divides by a zero-length bar.
- `export_has_short_bar_fault` said yes when no short bar fell inside the file's tempo map (`all()` of nothing), so a matching file was called "425 ms late" and Fix then failed.
- `fix -o SONG.mid` on `song.mid` overwrote the original on a case-insensitive disk: the guard now uses `samefile` too.
- Format 2 files read only the first pattern's tempo, so patterns that each start with a tempo aren't "two tempos on one tick" that nothing can fix.
- A read-only disk (EROFS) or no access (EACCES) gets the "choose a folder" question like a PermissionError.
- A WAV with 0 channels, under 8 bits or a short `fmt ` block is refused in a sentence.
- `repair()` keeps `smpte`.
Also from it: the zip updater refuses an installed Windows copy (mirroring a zip over it would delete the uninstaller) and writes `swap.bat` as Wavelength does, ASCII with every path as an argument, tested on CI's Windows with a "José Pérez" folder; the window clears the last batch when a new one starts, keeps the same file selected after a re-sort, keeps subfolder names when the notes checkbox re-checks, and names a fixed `.rmi` saved elsewhere `.mid`.

File reports say how many markers a file has ("10 markers. Make Ableton Set turns them into AbleSet sections."), counted once even when copied onto several tracks; `--json` has `markers`.

## Ableton Live sets for AbleSet (`ableton.py`, `ableton_gui.py`)

Markers become Live locators named the way AbleSet reads them (`> Verse`, the song's name at bar 1, `SONG END`), with the file's tempo map and time signatures. Command `midi-tempo ableton`, app File, Make Ableton Set (Cmd/Ctrl-L). Matthew asked for it on 2026-11-03, then for typed markers "at what bar and beat" with no limit, because some apps cap how many markers you get.

**The Live set format, and what's edited.** An .als is gzipped XML. Only three spans are rewritten, as text, everything else byte for byte: the locator list (`<Locators><Locators>…`), and the main track's tempo and time signature automation (`MainTrack` in Live 12, `MasterTrack` in 11), found through the `AutomationTarget Id` under `<Tempo>` and `<TimeSignature>` and the envelope whose `PointeeId` matches. A new set also gets the two `Manual` start values. Existing locators keep their XML exactly (info text and all); new ones copy the set's own locator shape and take ids above the highest. Times are quarter notes. `-63072000` is Live's "before the arrangement" time. A tempo jump is two `FloatEvent`s on the same `Time` (old value, then new); between points Live ramps linearly in beats. A time signature is one `EnumEvent`, value `(num - 1) + 99 * log2(den)` (4/4 = 201, 3/4 = 200, 7/8 = 303).

**Proven in Live 12.4.16 with AbleSet 3.1.9 running, 2026-11-03**, by opening real sets and reading AbleSet over OSC (`/getValues 127.0.0.1 PORT /setlist/*` to port 39051; `songs`, `songDurations`, `sections`, `activeSectionStart`): Fresh Air (148 tempo changes, 20 time signature changes) came back 348.939 s against the file's 348.93897; a three-song set (Fresh Air, Listening Forward, Felt Like It) gave every song's length to the millisecond and every section on its locator's beat; a song added after the last one landed on the next bar line; markers put onto an existing song kept its tempo. Tempo jumps: a 120 / 90 / 140 test read 32.381 s, the maths 32.381.

**A bare `>` locator hangs Live while AbleSet loads the set** (full CPU, the set never draws). The same set opened at once in Live 12 Beta, which doesn't load AbleSet, so it's AbleSet's. `has_no_name()` catches `>`, `>>`, `> +LOOP` and the like, and an unnamed marker becomes "> Section N". Reported to AbleSet support on 2026-11-03 (Matthew's thread "AbleSet 3.1.9 with VoiceOver", sent by Faith over iMessage at his OK).

**Reading the file.** The app's own tempo fixes are applied in memory first (a doubled tempo or a REAPER ramp note would put every later locator in the wrong place); `--project` undoes REAPER's padded short bars too. Markers are meta types 6 and 7, REAPER's leading `#` stripped, ramp hints skipped. The song's name is the file name tidied ("Fresh Air - midi track (tempo fixed)" is "Fresh Air"): the sequence name inside real files held a notation app's first staff ("Trumpet in B♭") or an old project's name as often as the song's. Only AbleSet's capitals are commands (`SONG END`, `STOP`, `AUTOSTOP`), so a band's "Stop" stays a section. A last marker named End becomes SONG END. When the music runs past it (Listening Forward rings 13 bars past "end" with the pedal down), SONG END stays at the marker and the tempo map runs to the music's end (`span_beat`), so the next song can't collide with it. Without an end marker, SONG END goes at the end of the bar where the last event (a note-off or a pedal release) falls. The song locator is always the song's start and never one of the file's markers, so a marker on bar 1 (Fresh Air's "intro") sits on the same beat as the song locator; AbleSet reads both (proven with Fresh Air). The preview, Song name and Marker name say so (1.9.2, Matthew's question on 2026-11-04). Checked 645 REAPER projects for a bar-1 marker repeating the song's title, which would make a section named like the song: none did, so nothing filters it. Retested the same day in Live 12.4.16 with AbleSet 3.1.9 over OSC: a song with Intro on bar 1 had Intro as the active section at the song's start; a song with Intro on bar 3 jumped to the song's start with no active section and Intro next, 2 bars on. That set also showed `--songs` listing the first song's SONG END under the second when they share a beat; `describe_set` now gives it to the song before.

**Straight from a REAPER project** (`rpp_markers`, `rpp_items_end`, `_rpp_maps`): markers (`MARKER idx seconds name flags`, names quoted with " ' or `), region starts (a region is two lines with flag 1 and the same index; its end is skipped), =START (the song starts there: everything shifts, and what's in force there becomes the first tempo and time signature) and =END (SONG END). Tempo from `rpp_tempo_points`, a first point after 0 gets the same tempo from 0; ramps (shape 0) become 32nd-note steps, each at the average tempo over its step, so every step boundary is exact, as REAPER's own export writes them. The music's end is the last item's end. Proven on "Fresh Air - tempo map and MIDI.RPP" against REAPER's MIDI export of it: same ten markers, worst marker 0.078 ms, tempo map within 0.093 ms at every quarter beat over 603 beats, 148 tempo changes both ways.

**Curved tempo in a set** (`LiveTempo`): a FloatEvent's CurveControl1X/1Y/2X/2Y shape the segment to the next point as a cubic Bezier, time on one axis and tempo on the other, both 0 to 1 across the segment. Seconds are the integral of 60/tempo along the curve's own parameter (Simpson, 400 steps). Proven by playing sets in Live 12.4.16 and timing the playhead (AbleSet's `/global/finePosition` against the wall clock, about ±30 ms of jitter): three curves from 120 to 60 BPM over 32 beats came out within that of the model (beat 2 to 16: Live 7.740 s, model 7.739, straight lines 8.190; c1 to beat 32: 16.919 / 16.903 / 21.165; c2: 27.560 / 27.588 / 21.165), and so did a plain ramp. **AbleSet's own song durations ignore curves** and roughly sample the tempo once per beat (37.943 s for all three curves; a straight ramp is 38.181), so never use them to check a ramp or a curve.

**Lyrics** (`midi_lyrics`, `lyric_lines`, `file_lyrics_typed`, `lyric_clips`, `LyricsEdit`, `LiveSet._lyrics_edits`): AbleSet shows lyrics from a MIDI track whose name has `+LYRICS`, one clip per line, the clip's name the line. From MIDI: lyric events (type 5), or a karaoke file's text events (/ new line, \\ new verse, @ headers). Only the track with the most lyrics is used: on real files several parts each carry their own ("Better Days" has Soprano 2, Alto 2 and Tenor 2) and mixing them read "PaPaPatience". Words join where at least a fifth of syllables mark word ends (a trailing space, or a hyphen); LilyPond's exports mark nothing, so syllables stay apart and the report says so. Lines break where the file says, else after a sentence end with a beat's gap, a comma with 1.5 beats, a whole bar's rest, a section, or nine words with a beat's gap (that last only when words are known). Each clip lasts until the next line.
- **Where the clips go:** a new set renames Live's own empty MIDI track; a set with a `+LYRICS` track gets them there (onto a song, its old clips in the song's range are replaced); otherwise one of the set's own MIDI tracks is copied (`_clone_track`): emptied of clips, devices (`_balanced_end` for nested racks) and automation, renamed, given the next track id, and every pointee renumbered from NextPointeeId. Copying the set's own track keeps its sends and its Live version; a set with no MIDI track is told to add one.
- **Clips are shaped like a clip from the set itself**, else one from the installed Live's own sets (`installed_clip_model`), else `BUILTIN_CLIP`; emptied of notes and envelopes.
- **Two traps, both found in Live:** the copy kept 131 `ControllerTargets.N` ids, which Live refused as "corrupt (non-unique Pointee IDs)" and offered to repair (the pattern is now `POINTEE`, any tag containing Target, plus Pointee; 27 real sets have no duplicates under it, and `_verify` checks it); and clips listed out of time order were in the file but AbleSet showed no lyrics for the earlier song, so the clip list is always sorted.
- **From the review of these features (2026-11-03), each reproduced and fixed:** clip lists are matched by nesting (`_balanced_end`, `_empty_all`), because a clip's own envelope has an Events list inside and the first `</Events>` isn't the track's (Live's "Patience" demo broke on it); `_balanced_end` reads `<Devices />` as closed (a rack with an empty chain); the copy's take lanes are emptied (their clips had envelopes pointing into the source track), Freeze is off and SelectedDevice 0; lyric clips stop at the song's end, by bar or by time, and lines past it are named, never run into the next song; a set started from your own set renames its first MIDI track only when it's empty (no clips, no devices), else copies it; onto a song takes lyrics alone; the window reads a REAPER project's bars for typed markers and lyrics, and No File drops the last file's lyrics; REAPER backups (.rpp-bak) are projects, a project's name is kept whole ("tempo map and MIDI" isn't trimmed), markers after =END are left out and named, an empty project file says it may not be downloaded, and seconds-to-beats noise (118.9999999999995) is snapped to a 3840th of a beat. **Reading a set back** (`describe_set`, `midi-tempo ableton --songs`): every song and its sections by bar, both kinds AbleSet uses, locators and Sections-track clips (`section_clips`). **Into a set you have** (`add_to_set`): songs are AbleSet's (`is_song_locator`: not `>`, `*`, `[`, a command, or a digits-only name when there's a Sections track). Markers past where the song ends in the set (the next song, or its SONG END) are left out and named; a guessed end is never said to be lost. The copy is `(markers added)`; `--update-set` writes the set itself after copying it to `(before markers)`. Every write goes to a `.check` file first, is read back (`_verify`: the XML parses, ids are unique, every locator is there, and with a tempo map written each plays within 1 ms of its marker), then renamed into place.

## Updates (Sparkle, WinSparkle, `update.py`)

**The Mac app and installed Windows copies use Sparkle 2.10.0 and WinSparkle 0.9.4** (`sparkle.py`, `winsparkle.py`, the way Wavelength does), from 1.8.0. Every update is signed with the EdDSA key in the Studio's login Keychain, **the same key as Wavelength's** ("Private key for signing Sparkle updates", account ed25519; public half `SUPublicEDKey` in `build_app_support.py`). One key for both apps, so one thing to back up; losing it means no Sparkle-installed copy of either accepts another update. Neither checks by itself (`SUEnableAutomaticChecks` NO, WinSparkle automatic 0): the app's own once-a-day GitHub check puts "update available" in the title and report, and Help, Check for Updates opens Sparkle's window. The feeds are `releases/latest/download/appcast.xml` and `appcast-windows.xml`, written and signed by `tools/release_mac.py` (via `tools/appcast.py`) after notarizing. `sparkle_bin()` prefers an existing sign_update from Wavelength's or the charting suite's build cache, because the Keychain's Always Allow is tied to that exact path; from there it signed without a prompt on 2026-11-03. The self-test fails a Mac build without Sparkle or a Windows build without WinSparkle.

Copies older than 1.8.0, and a Windows copy run from the zip, use `update.py`: the app asks `api.github.com/repos/Matthew2244/midi-tempo-fix/releases/latest` at most once a day (time stored with `wx.Config`) and on Help, Check for Updates. ## Rules the code keeps

- **The original file is never written.** Fixes go to `<name> (tempo fixed).<ext>`; the code refuses to overwrite the input.
- **Every fix verifies itself** by reading the saved file back: no faults left, and the playback time of every non-tempo event matches the original within a microsecond. On failure the copy is deleted.
- **Nothing beyond the four faults is changed.** No re-quantizing, no rounding tempos, no PPQ change.
- **A Live set is never written over.** New sets refuse an existing name; a set you have gets a "(markers added)" copy, or with `--update-set` a "(before markers)" backup first. Every set goes to a `.check` file, is read back (`_verify`), and only then takes its name.
- **Output is sentences, written once.** No "(s)" plurals (`n()` in core), no progress spam. A screen reader user hears one clean report.
- **In the app, focus goes to the report after every action.** All actions are in the File menu with shortcuts as well as on buttons.

## Settings and scripting

The app remembers, through `wx.Config` (named `gui.CONFIG_NAME`: the app's name, or `MIDI_TEMPO_FIX_CONFIG` for test runs), whether notes are checked and the last folder files were chosen from, so dialogs open there, and the Make Ableton Set choices: `ableton_plain`, `ableton_quick`, `ableton_song_end`, `ableton_into_existing`, `ableton_last_set`, `ableton_template`. `midi-tempo check --json` prints machine-readable results (per-file problems, doubled tempos, note counts, optional comparison) for scripts and other tools.

## Comparing (universal)

`compare_with(mf, path)` picks by extension: any MIDI file goes to `compare_midi`, a `.rpp` to `compare_project`. The app's button and the command's `--compare` (alias `--project`) both use it. The point is app-neutral: export from one app, import into another, export again, compare the two.

`compare_midi` checks the tempo map beat by beat (quarter-beat steps, each file at its own resolution, so a 480-PPQ Logic export compares cleanly with a 960-PPQ REAPER one), then every note: starts in seconds grouped by channel and key, matched in order, ignoring tracks because apps merge and split them. Differences under `SAME_MS` (2 ms) are tick rounding and count as matching. When the note counts differ it lists which keys and stops: matching by order means nothing once notes differ, and the "moved by" number would be garbage (it was, -322 seconds, before that early return).

### REAPER project comparison

`compare_project` reads a `.RPP`'s `<TEMPOENVEX>` points (`PT seconds bpm shape ...`; shape 0 = ramp to the next point, 1 = square) and computes beat times with ramps linear in time: beats = seconds × (start + end) / 120. That model was confirmed against REAPER's own export to the microsecond.

## Screen reader behaviour, and why the code looks the way it does

Tested with VoiceOver on macOS 26 on 2026-10-11, driving the real app with keystrokes and reading `content of last phrase` from VoiceOver:

- **The report needs an explicit label on macOS.** wx has no API for it, so VoiceOver said only "text". `mac_accessibility_label()` sets `accessibilityLabel` on the scroll view and its text view through the Objective-C runtime (ctypes, no extra dependency). It now says "Report, text". Windows readers take the name from the static label created just before the field, so keep that label directly before the report in creation order.
- **A field that already has focus is not re-read when its text changes.** After Fix, VoiceOver kept reading the old report. `show()` steps focus to the Choose button and back after 150 ms when the report is already focused; VoiceOver then reads the new result in full.
- **Tab order is creation order.** Buttons are created in on-screen order: Fix, Show cleaned files, Compare with another file.
- **The update dialog's second button must be titled exactly "Cancel".** macOS alerts give Escape only to a button with that title. As "Not now" (and earlier as Yes/No), Escape did nothing and the dialog could only be left by Install or by hunting for the other button. Found in the VoiceOver pass; checked fixed the same way.
- **A checkbox reads its state** ("checked checkbox" / "unchecked"). Toggling it re-checks the files into the report without moving focus, so the user stays on the checkbox.
- **Move focus to the report a moment after any dialog closes.** Right after a file dialog, macOS restores focus itself; setting it then made VoiceOver say only "Report scroll area" and skip the text. `show()` now defers the focus move by 250 ms; VoiceOver then reads the whole result after Choose and after Compare.
- The saved line is short ("Saved next to the original as ...") because a full path is noise spoken aloud and clutter on screen. The command line keeps the full path for scripts.
